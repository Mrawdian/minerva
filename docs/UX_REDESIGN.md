# UX / platform redesign

> Product-surface redesign to move Minerva from "pipeline/corpus" mode to
> "surface & conversion" mode, now that the corpus has a usable mass (106 fiches).
> Framing validated 2026-07-30; built in cadenced phases.

## North star

Make it undeniable in 5 seconds that **Minerva is a decision-ready intelligence
layer on the Chinese open-source hardware ecosystem — not a repo directory.**
B2B angle (tech scouting, competitive intelligence, sourcing/BOM, edge-AI
benchmarking) in language that stays accessible to engineers — never
corporate-empty.

## Constraint

Static-first (single-file HTML generated by `build_site.py` / `build_dashboard.py`;
no backend yet). V1: everything static is free/proof; paid features are honest
waitlist CTAs, never a fake connected zone. Backend-dependent items (live
freshness, saved watchlists, API) are marked and deferred (roadmap).

## The three decisive shifts

1. **Fiche-first, not grid-first.** The first proof (landing *and* dashboard) is a
   real, fully-rendered fiche with its decision layer foregrounded — above all
   the **Western-equivalent mapping**, plus Chinese specificity, maturity and the
   **confidence tier**. That is what proves "decision-ready", not a card grid.
2. **Use cases as first-class.** Four cases (tech scouting, competitive
   intelligence, BOM/sourcing, edge-AI benchmarking), each wired to a real view.
3. **One continuous journey** free → proof → conversion, with consistent CTAs
   across landing / dashboard / plans.

1. **Hero** — one value sentence + subline (Gitee+GitHub → EN/FR fiches with
   Western equivalent) + primary CTA `Explore the live dashboard` + capture CTA
   `Get the weekly brief`.
2. **Proof fiche** — one *real* rendered fiche (pulled from the corpus at build
   time), decision fields annotated. The anti-directory "aha".
3. **Use cases** — 4 cards: job-to-be-done + concrete example + link to a view.
4. **How it works** — 3 condensed steps (collect Gitee+GitHub → semantic score →
   bilingual LLM enrichment).
5. **Honest numbers** — 106 fiches, 15 orgs, domains (Embedded 55 / Edge AI 45 /
   Robotics 9 / IoT 2), vendor share ~88%.
6. **Trust & sources** — official APIs, public metadata, link-back, transparent
   confidence (links to SOURCES / SCORING).
7. **Conversion** — newsletter (free capture) + Pro preview → waitlist.

## Ideal dashboard (Phase 2)

- Opens on a **highlighted real fiche**, not a cold grid.
- Two-pane: compact filterable list (left) + fiche detail (right). **Detail panel
  stays light — fast exploration must survive** (owner decision): no heavy /
  invasive panel; a tap swaps the detail, keyboard/scan-friendly.
- Filters exposed as **use-case presets** on top of the existing
  domain/type/score/confidence filters.
- Confidence badges made legible + explained in one click (link to SCORING).
- **No regression**: full-text search, sort, existing filters preserved.

## Free vs paid

| Zone | Free (V1, static) | Paid (Pro/Enterprise — waitlist in V1) |
|---|---|---|
| Dashboard | full public snapshot (106 fiches), filters, search | hosted freshness, history/timeline, saved watchlists |
| Fiches | all readable + shareable | export (JSON/PDF), API feed |
| Newsletter | free weekly brief (capture) | custom per-watchlist digests |
| Watch | default orgs | custom competitor/org watch + quarterly report |

Principle: the **proof is free and generous** (the whole decision-ready corpus);
we gate **freshness, history, automation and bespoke watch** — what a pro pays for.

- Secondary: `Go Pro / Join the waitlist` (freshness + custom watch).

### V1.1 — build order (revised)

The intelligence-console direction is right, but its promises ("what changed",
"where's the signal") depend on **time**. We have neither hosted freshness nor an
accumulated history yet, so V1.1 stays static-first and honest, and the history
artifact is built **as the foundation — before the signal layer**, not as polish.

Correct order:

1. **Phase 1 (done)** — landing + publication hygiene.
2. **Phase 2 (done)** — dashboard explorer.
3. **Foundation — history artifact (do this next, before any signal UI).** A
   committed, machine-readable run artifact that becomes the single source of
   truth for signal, briefings and rankings. Without it, the "signal" is a UI
   illusion (see *Technical preconditions* below).
4. **Phase 3 — Signal layer.** A light "Signal" strip on the dashboard reading the
   artifact (NEW / MODIFIED / DELETED for the last run), a "recently changed" sort
   and a vendor/org facet in Explore, and an explicit **"as of {last_run}"** stamp
   everywhere. No new top-level page.
5. **Phase 4 — Fiches → dossiers.** Enrich the existing fiche pages: related repos
   (same domain/owner), confidence / Western-equivalent / Chinese-specificity as
   primary reading layers, source links. No user notes, no personal edits, no
   persistent watchlist.
6. **Phase 5 — Briefings.** A simple web brief generated from the *same* artifact
   as the newsletter (one selection, one run, no double truth). Reuse the
   newsletter as a distribution format, not a separate content stream.

Two changes vs the first draft: the history artifact **moves to the front** (it is
the architectural lock, not the finish), and signal/briefings **read that
artifact**, not `output/diff_*.md` (gitignored + markdown, unreadable by the
static site) or the last-run-only `state.json`.

### V1.1 vs V2 scope

**In V1.1** (static-first, sustainable today):

- Light signal strip on the dashboard (reads the history artifact).
- Explore enriched with useful sort + vendor/org facets.
- Fiches leaning toward analyst dossiers.
- Simple briefings backed by real runs, sharing the newsletter's source of truth.

**Not in V1.1** (deferred to V2):

- Relational map.
- Multi-run timeline.
- Persistent watchlists.
- Personal analyst workspace.
- Any "live" / "real-time" wording.

**V2 — only after two things exist for real:** regular hosted runs *and* an
accumulated history. Then, and only then: living console, multi-run timeline,
momentum ranking, richer vendor dossiers, relational mapping, and possibly an API.
The V1.1 history artifact is the seed that makes this V2 true instead of fictional.

### Honesty guardrails (V1.1)

The signal layer must never imply change or freshness it cannot back with data.
Four non-negotiable guards:

1. **`first_seen` is bootstrapped explicitly.** "NEW" is only true against a prior
   run. On the first committed run there is no prior state, so we set
   `first_seen = build date` for the existing corpus as an assumed baseline (not
   "new"), then accrue truthfully from the next run on. **No NEW badges on day one.**
2. **DELETED is handled cleanly.** A removed fiche = a page that no longer exists,
   so "DELETED" has nothing to anchor to. Either keep a light tombstone (name +
   "removed at run X") or mention it only in the brief — never a dangling badge.
3. **Vendor pages/sections only with enough mass.** With thin domains (IoT 2,
   Robotics 9), a vendor view on a small org reads as filler. Gate vendor sections
   to orgs with **≥ ~5 fiches**, and prefer a *section* (inside dashboard/fiche)
   over a new top-level page.
4. **A fresh run before public launch.** Even with "as of {last_run}" everywhere,
   a signal strip dated weeks back feels stale. Hosted freshness is V2, but
   operationally: run the pipeline once, fresh, right before the public push so the
   "as of" date is credible at launch.

### Technical preconditions for a real signal layer

The signal must be data-backed, not cosmetic. Before Phase 3 (signal UI):

- **A committed, machine-readable run artifact** (e.g. append-only JSONL) the
  static build can read. Today's diffs (`output/diff_*.md`) are gitignored and
  markdown; `state.json` keeps only the *last* `pushed_at`/score — neither can feed
  an honest signal layer.
- **Per-repo fields**: `first_seen`, `last_changed`, `last_run`, `modified_flag`,
  full `score`, and a build date — enough to compute NEW / MODIFIED / DELETED and
  "recently changed" without inventing anything.
- **One source of truth**: signal strip, briefings and any ranking read the *same*
  artifact. The newsletter's selection logic must draw from it too, or the web
  brief and the newsletter will drift.
- **No live wording** until hosted freshness exists; the artifact records *runs*,
  the UI states "as of {last_run}".
